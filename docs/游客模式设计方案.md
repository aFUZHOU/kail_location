# 游客模式设计方案

> 目标：**未登录用户无需注册/登录即可访问并使用模拟功能**；每位游客享有 **100 次免费模拟机会**，
> 已用次数被准确记录、校验并持久化；次数用尽后引导登录/注册。方案与现有
> MVVM + `UsageManager` 门控 + RuoYi 后端的架构保持一致。

---

## 1. 总体架构

```
┌───────────────────────────────────────────────────────────────┐
│ UI 层（Compose）                                                │
│  LocationSimulationScreen   游客剩余次数提示 / 用尽引导对话框    │
│  DrawerHeader               未登录时显示"游客模式 · 剩余 N 次"  │
└──────────────────────────┬────────────────────────────────────┘
                           │ StateFlow / mutableStateOf
┌──────────────────────────▼────────────────────────────────────┐
│ 门控层 auth/UsageManager.kt（唯一入口，8 个 ViewModel 共用）      │
│   canStartSimulation → 未登录走 GuestModeManager                 │
│   consumeSimulation  → 未登录走 GuestModeManager                 │
└──────────────────────────┬────────────────────────────────────┘
                           │
┌──────────────────────────▼────────────────────────────────────┐
│ auth/GuestModeManager.kt                                        │
│   游客 ID(UUID) │ 本地缓存(SharedPreferences) │ 离线兜底 + 对账   │
└──────────────────────────┬────────────────────────────────────┘
                           │ OkHttp（guest-id / device-id 头）
┌──────────────────────────▼────────────────────────────────────┐
│ 服务端 backend/（RuoYi 风格，仓库外后台工程合并）                 │
│   /guest/simulation/check │ use │ sync                          │
│   kail_guest_simulation_quota 表（服务端权威）                   │
└───────────────────────────────────────────────────────────────┘
```

**关键决策：门控入口不变。** 8 个 ViewModel（位置/路线/导航/NFC/WiFi/基站/摄像头/独立模拟）
本来就调用 `UsageManager.canStartSimulation` → `consumeSimulation`，本次只改
`UsageManager` 内部分支：未登录时由"直接拒绝"改为"走游客配额"，**所有模拟功能自动获得游客能力**，
无需逐页面改造。

## 2. 游客身份与配额模型

| 项 | 设计 |
| --- | --- |
| 游客 ID | 首次启动生成 UUID，存独立 SharedPreferences `guest_prefs`；退出/重新登录不重置 |
| 免费额度 | 100 次（`GuestModeManager.GUEST_FREE_TOTAL`，与服务端 `total_limit` 默认值一致） |
| 计数口径 | **总量制**（非每日刷新），与服务端 `used_count` 单调递增对应 |
| 权威方 | 服务端为准；本地缓存仅作离线兜底与 UI 展示 |
| 无限次 | 服务端把 `total_limit` 置 -1（补偿开关）时，客户端 `limit=-1` 直接放行 |

### 2.1 本地存储（`guest_prefs`）

| key | 含义 |
| --- | --- |
| `guest_id` | 游客 UUID |
| `guest_used` | 已用次数（本地视图，含离线增量） |
| `guest_limit` | 总上限（默认 100，-1 无限） |
| `guest_pending` | 离线消耗尚未对账到服务端的增量 |
| `guest_last_sync_ts` | 上次成功同步时间（5 分钟节流） |
| `guest_synced_once` | 是否与服务端同步过 |

### 2.2 服务端存储（`kail_guest_simulation_quota`）

| 列 | 含义 |
| --- | --- |
| `guest_id` | 游客 UUID（唯一索引 `uk_guest_id`） |
| `device_id` | 设备指纹 ANDROID_ID（索引，风控用） |
| `used_count` | 已用次数 |
| `total_limit` | 总上限，默认 100，-1 表示无限 |
| `last_use_time` | 最近一次消耗时间 |

DDL 与放行配置见 `backend/sql/kail_guest_simulation_quota.sql`。

## 3. 核心流程

### 3.1 游客开始模拟（正常在线）

```
点击"开始"
  └─ ViewModel.toggleSimulation/startSimulation
       ├─ UsageManager.canStartSimulation(app)
       │    └─ 未登录 → GuestModeManager.canStartSimulation
       │         ├─ syncIfNeeded()            # 5 分钟节流；pending>0 强制同步
       │         │    ├─ GET  /guest/simulation/check   # 拉取 used/limit
       │         │    └─ POST /guest/simulation/sync    # pending>0 时对账
       │         └─ remaining = limit - used > 0 → true
       └─ UsageManager.consumeSimulation(app)
            └─ 未登录 → GuestModeManager.consumeSimulation
                 ├─ POST /guest/simulation/use           # 原子扣减
                 │    成功 → 本地 used = 服务端 used + pending
                 │    1401 → 本地置用尽 + 触发引导
                 └─ 启动前台服务（原有逻辑不变）
```

### 3.2 离线兜底与对账

网络异常时 `guestUse` 失败 → 转入 `offlineConsume`：

1. 本地 `used < limit` → `used+1`、`pending+1`，放行（日志标记离线扣减）；
2. 本地已用尽 → 按用尽处理（触发引导）；
3. 下次联网（App 启动或节流到期）→ `check` 拉取服务端基准，再 `sync(delta=pending)`
   补记；服务端 `LEAST(used+delta, limit)` 截断，**幂等且不超上限**；
4. 对账失败 → 本地叠加 pending（`server_used + pending`），保证已发生的消耗不丢失。

> 对账流程由 `syncMutex` 串行化：避免并发 sync 把同一批 pending 重复上报；
> 对账成功后只从 pending 中扣除**已成功对账的数量**，对账窗口期内新产生的
> 离线消耗继续保留，不会丢失。

> 首次安装即离线使用的场景：本地按初始值（0/100）放行，联网后由服务端对账兜底。
> 若该 guest_id 在服务端已有记录（如清除数据前用过），`check` 会直接恢复真实已用次数。

### 3.3 次数用尽引导

```
GuestModeManager.onExhausted()
  ├─ exhaustedEventId += 1        # UI 事件（可重复触发）
  └─ Toast："游客免费次数已用完，登录后可继续使用"

LocationSimulationScreen 监听 exhaustedEventId
  └─ 弹出 GuestQuotaExhaustedDialog
       ├─ "登录 / 注册" → 跳转 LoginActivity（邮箱验证码，登录即注册）
       └─ "稍后再说"   → 关闭
```

- 在任意模拟页触发用尽时：当场 Toast；返回主壳时对话框仍在（事件未消费），引导不丢失；
- 抽屉头部常驻显示"游客模式 · 剩余 N 次"，用尽后显示 0。

### 3.4 与登录体系的衔接

| 场景 | 行为 |
| --- | --- |
| 游客 → 登录 | 登录成功后门控切到会员逻辑（订阅/会员免费次数）；游客配额保留不变 |
| 会员 → 退出登录 | 重新变为游客，同一 `guest_id` 的配额继续生效（防"登出刷配额"） |
| 清除数据/重装 | 生成新 `guest_id`；服务端保留旧 ID 记录，可按 `device_id` 风控（默认关闭） |

## 4. 接口契约（服务端）

请求头：`tenant-id: 1`、`guest-id: <UUID>`、`device-id: <ANDROID_ID>`；响应遵循 RuoYi 约定。

| 方法 | 路径 | 请求 | 成功响应 data | 失败 |
| --- | --- | --- | --- | --- |
| GET | `/guest/simulation/check` | - | `{"used":12,"limit":100,"remaining":88}` | `code!=0` → 客户端按网络异常走离线缓存 |
| POST | `/guest/simulation/use` | `{}` | 扣减后配额 | `code=1401` → 次数用尽（客户端专门识别） |
| POST | `/guest/simulation/sync` | `{"delta":3}` | 对账后配额 | `code!=0` → 保留 pending 下次重试 |

并发正确性：扣减使用
`UPDATE ... SET used_count = used_count + 1 WHERE guest_id = ? AND used_count < total_limit`，
受影响行数为 0 即用尽，无超卖窗口；建记录用 `INSERT IGNORE` + 唯一索引。

## 6. 边界情况与错误处理

| 场景 | 处理 |
| --- | --- |
| 服务端返回 1401（用尽） | 本地 `used=limit`，触发 Toast + 对话框，不启动服务 |
| 网络超时/断网 | 离线兜底扣减并记 `pending`；下次联网 `sync` 对账（LEAST 截断，幂等） |
| 对账失败 | 本地视图 = 服务端 used + pending，不丢消耗；pending 保留重试 |
| 服务端补偿无限次（limit=-1） | 客户端直接放行；`use`/`sync` 服务端跳过扣减 |
| 并发启动（双击/多页面） | 服务端条件 UPDATE 行锁保证不超卖；本地有 `_isStarting` 防重 |
| 清除应用数据 | 新 `guest_id`；服务端旧记录仍在，可按 `device_id` 限流（默认关） |
| 登录后用尽会员次数 | 走原会员分支（Toast"今日免费次数用完"），不受游客逻辑影响 |
| guest-id 缺失/为空 | 服务端 400；客户端 `consumeSimulation` 返回 false 并记日志 |
| `Settings.Secure.ANDROID_ID` 不可用 | `device-id` 传空串，不影响功能（仅风控维度缺失） |

## 7. 安全与防滥用

1. **服务端权威**：一切已用次数以服务端为准，本地篡改（root 改 prefs）在下次同步时被纠正；
2. **退出登录不重置配额**：游客 ID 独立持久化，杜绝"登出/登录"循环刷额度；
3. **设备指纹**：`device_id`（ANDROID_ID）随请求上报，
   `GuestSimulationServiceImpl.DEVICE_GUEST_LIMIT` 设为正整数即可限制同设备反复"清除数据"刷配额
   （默认 `-1` 关闭，避免误伤重装用户）；
4. **接口匿名放行仅限 `/guest/simulation/**`**，不波及会员/订阅等敏感接口；
5. **无限次补偿**只通过服务端 `total_limit=-1` 开启，客户端无法自行伪造。
